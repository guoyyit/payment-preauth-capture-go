# 本地支付预授权与捕获结算服务（Go）

纯本地实现的支付预授权（pre-authorization）/捕获（capture）/退款（refund）/
结算（settlement）服务。账户与请求数据全部在本地构造与落盘，**不依赖任何外部服务、
数据库或网络**。每次业务操作都把全量状态原子写入单个 JSON 快照文件，进程重启后
自动恢复。

## 能力总览

1. 预授权冻结账户资金，携带有效期；到期后剩余冻结额自动释放，释放事件永久留痕。
2. 支持部分捕获与部分撤销；捕获 + 撤销累计不得超过冻结额；并发下不超额、不重复释放。
3. 支持预授权金额调整：上调重新校验可用余额，下调立即释放差额；与捕获/撤销并发结果确定。
4. 支持对已捕获金额全额/部分退款；退款累计不得超过“已捕获且未退款”金额。
5. 按结算周期汇总已捕获净额生成批次；同一捕获不会重复计入；批次重试与生成均幂等。
6. 全程状态机约束，非法转移返回可区分的错误码；重复提交返回首次结果且无二次副作用。
7. 崩溃恢复：已确认操作不丢失；未确认（open）结算批次在重启时按策略回滚，可重试。

## 金额与账户模型

- 金额使用最小货币单位（分）的 `int64`（`domain.Money`），避免浮点误差。
- 账户恒等不变量：
  - `Available = Balance - Frozen`（可用 = 总额 − 冻结，冻结是总额的一部分）；
  - 捕获：`Balance -= amount`、`Frozen -= amount`（资金离开冻结桶并完成扣款）；
  - 释放（撤销/到期/下调）：`Frozen -= amount`（资金回到可用，不动总额）；
  - 退款：`Balance += amount`（已扣款项退回客户）。
- 预授权不变量：`Captured + Released <= Amount`，`Remaining = Amount - Captured - Released`。
- 账户冻结额恒等于其名下所有**有效**预授权 `Remaining` 之和；恢复时据此重算校验。

## 状态模型

预授权（`AuthStatus`）：

```
                 capture / void / adjust-down 用尽额度
   active ───────────────────────────────────────────────► closed
     │
     │ 到达 ExpiresAt（被动访问触发或 SweepExpired 扫描）
     └──────────────────────────────────────────────────► closed
```

- `active`：冻结生效，可捕获、撤销、调整。
- `closed`：额度用尽（`Remaining==0`）或已到期；不可再捕获/撤销/调整。
  - 额度用尽关闭后继续操作返回 `exceed_remaining`；
  - 到期关闭后操作返回 `auth_expired`，二者可区分。
- 到期处理是惰性 + 主动两种：任意写操作访问到已到期预授权时自动释放剩余额；
  `SweepExpired()` 可批量扫描，重复扫描幂等，绝不重复释放。

捕获（`Capture`）：带 `Refunded`（累计退款）、`Settled` 与 `BatchID`（所属批次）。

结算批次（`BatchStatus`）：

```
 generateBatch                 ConfirmBatch（可安全重试）
 ───────────► open ───────────────────────────────────► confirmed
                │  进程在确认前崩溃
                └─ 重启时回滚：删除批次，释放其对捕获的占用，可重新结算
```

- `open`：批次已生成，捕获被该批次锁定，期间拒绝退款（待定窗口）。
- `confirmed`：结算完成；此后这些捕获的退款窗口关闭（返回 `capture_already_settled`）。
- `SettleCycle` 在同一个临界区内“生成并确认”，是对外推荐的单周期原子结算入口。

释放事件（`ReleaseEvent`）有三种原因，全部追加留痕、可按预授权查询：
`expiry`（到期）、`void`（主动撤销）、`adjust_down`（额度下调差额）。

## 并发与一致性

- 服务内所有变更由**同一把互斥锁**串行化，配合“整份快照原子写盘”，
  在单进程内保证线性一致：不会出现超额捕获、重复释放、重复结算。
- 调整与捕获/撤销并发：后到者基于前者已提交的结果重新校验，最终状态唯一确定
  （见 `TestAdjust_ConcurrentWithCapture_IsDeterministic`）。
- 结算与退款并发只有两种确定结局，由锁顺序决定：
  1. 结算先提交 → 退款被拒，批次按捕获全额计入；
  2. 退款先提交 → 退款生效，批次按捕获净额（金额−退款）计入。
- 金额下调释放差额时以“当前实际冻结额 − 目标冻结额”计算，
  因此即使下调在捕获之后到达，也不会把已离开冻结桶的资金重复释放。

## 幂等语义

每个写操作都接受 `IdempotencyKey`，执行器（`runIdempotent`）行为：

- **首次提交**：执行业务逻辑，把成功响应或业务错误（含错误码）连同
  操作种类、请求参数指纹一起落盘。
- **重复提交（同键 + 同种类 + 同参数指纹）**：不再执行任何副作用，
  直接返回首次的响应；首次失败则重放首次的业务错误。
- **同键但操作种类不同或参数指纹不同**：返回 `duplicate_request_mismatch`。

幂等记录本身也在快照中持久化，因此进程重启后依然可安全重放
（见 `TestCrashRecovery_StateSurvivesRestart`）。

## 持久化与崩溃恢复

- 写盘采用“临时文件 + fsync + 原子 rename + 目录 fsync”，
  崩溃时只会看到上一个完整版本，不会出现半写文件。
- 每次业务操作是一次全量原子提交，因此不存在“半完成”操作：
  - 已确认（落盘）的操作不丢失；
  - 未落盘的操作等同于从未发生，客户端可用原幂等键重试。
- 启动恢复（`recoverSnapshot`）：
  - 回滚所有 `open` 批次并释放其对捕获的占用（既定回退策略）；
  - 依据有效预授权重算账户冻结额并校验 `Balance >= Frozen` 等不变量；
  - 校验每张预授权 `Captured + Released <= Amount`；
  - 快照损坏时直接报错，拒绝以不一致状态启动。

## 配置项（`service.Config`）

| 字段           | 含义                                                        | 默认         |
|----------------|-------------------------------------------------------------|--------------|
| `SnapshotPath` | 快照文件路径；空串表示纯内存模式（不落盘，适合单元测试）     | 空（内存）   |
| `Now`          | 时钟函数，注入后可精确模拟到期与结算周期，便于测试           | `time.Now`   |

ID 默认随机生成（`auth-*`、`cap-*`、`rel-*`、`ref-*`、`adj-*`、`batch-*`），
各请求也支持显式传入业务 ID。

## 错误码（可区分）

| 错误码                     | 触发场景                                   |
|----------------------------|--------------------------------------------|
| `not_found`                | 账户/预授权/捕获/批次不存在                |
| `invalid_amount`           | 金额非正、TTL 非正、结算周期非法、余额为负 |
| `insufficient_funds`       | 冻结/上调时可用余额不足                    |
| `illegal_state`            | 对 open 批次锁定的捕获发起退款等           |
| `exceed_remaining`         | 捕获/撤销超过剩余冻结额；额度用尽后操作    |
| `exceed_refundable`        | 退款超过“已捕获且未退款”金额               |
| `auth_expired`             | 对已到期预授权发起写操作                   |
| `adjust_below_used`        | 下调目标低于已捕获+已释放                  |
| `duplicate_request_mismatch` | 幂等键被不同操作种类或参数复用            |
| `settle_empty`             | 周期内没有可结算的未结算捕获               |
| `capture_already_settled`  | 对已随批次确认的捕获发起退款               |

## 运行与测试

```bash
go build ./...                 # 构建
go vet ./...                   # 静态检查
go test ./... -race            # 全部测试（含竞态检测）
go run .                       # 本地演示；首次执行业务流程并写 data/snapshot.json
go run .                       # 再次运行：从快照恢复并做幂等重放
```

测试覆盖的关键场景：

- 并发捕获不超额、捕获与撤销并发不重复释放（`-race`）；
- 到期被动释放、`SweepExpired` 扫描及其重复调用幂等；
- 金额上调余额校验、下调即时释放、调整与捕获高并发竞争（50 轮）；
- 退款全额/部分/边界、未知捕获、退款与捕获并发一致性（30 轮）；
- 批次净额汇总、重复结算不重复计入、批次确认重试幂等、结算与退款并发；
- 重启后冻结/捕获/退款/批次状态一致、幂等记录保留、open 批次回滚；
- 快照往返、损坏快照拒绝启动、冻结额重算。
